\chapter{System Design and Implementation}

This chapter presents the complete technical design and implementation of the
platform. It covers the overall system architecture, database design, backend
implementation, frontend structure, the AI pipeline, H5P integration, and
the security model.

% ─────────────────────────────────────────────────────────────────────────────
\section{Overall System Architecture}

\subsection{Architectural Overview}
\label{sec:architecture}

The platform follows a three-tier architecture consisting of a
\emph{presentation tier} (React SPA), an \emph{application tier}
(Express.js REST API), and a \emph{data tier} (SQLite database managed via
Sequelize ORM)~\cite{bass2012}. External service dependencies are limited to
Groq (primary cloud AI), the Anthropic Claude API (cloud fallback AI),
and Ollama (local AI fallback); all other components run within the
local server process.

Figure~\ref{fig:architecture} shows the complete system architecture.

\begin{figure}[H]
  \centering
  \input{figures/fig_system_architecture}
  \caption{Three-tier system architecture of the H5P Interactive Video Platform}
  \label{fig:architecture}
\end{figure}

The architectural goals that drove the design are:

\begin{itemize}
  \item \textbf{Separation of concerns.} The frontend communicates with the
  backend exclusively through a versioned REST API. No server-side rendering
  is used, ensuring that the UI can be developed and tested independently.

  \item \textbf{AI provider independence.} The AI pipeline routes requests
  through a three-provider priority chain: Groq (primary) $\to$ Ollama
  (local fallback) $\to$ Claude (cloud fallback). The frontend receives
  identical suggestion structures regardless of which provider was used.

  \item \textbf{H5P library isolation.} All H5P operations are delegated to
  the \texttt{@lumieducation/h5p-server} library, ensuring compliance with
  H5P specification changes without requiring platform-level modifications.

  \item \textbf{Stateless REST API.} The API server is stateless; all
  session state is carried by the JWT Bearer token in the
  \texttt{Authorization} header. This design supports horizontal scaling.
\end{itemize}

\section{Database Design}

\subsection{Database Technology Selection}

The platform uses SQLite as its database engine, managed through the
Sequelize v6 ORM~\cite{sqlite2023,sequelize2023}. SQLite was selected
over PostgreSQL for four reasons:

\begin{enumerate}
  \item \textbf{Zero-configuration deployment.} SQLite stores the entire
  database in a single file (\texttt{h5p.db}), requiring no separate
  database server process, no connection string configuration, and no user
  or password management. This substantially lowers the barrier to local
  installation for educational institutions with limited IT support.

  \item \textbf{Sufficient capacity.} SQLite comfortably handles databases
  in the hundreds-of-gigabytes range with concurrent reads and moderate
  concurrent writes---far exceeding the expected scale of a
  single-institution deployment.

  \item \textbf{Future migration path.} Sequelize's dialect abstraction
  layer allows migration to PostgreSQL (or MySQL) by changing a single
  configuration variable when institutional scale demands a dedicated
  database server.

  \item \textbf{Native JSON support.} Sequelize's \texttt{DataTypes.JSON}
  mapping stores the H5P content parameter structure as a native JSON column,
  enabling efficient reads without schema migration when H5P content
  structure changes.
\end{enumerate}

The data model is deliberately minimal, comprising two primary entities:
\textbf{User} and \textbf{Video}. The relationship is one-to-many: one user
may own many videos; each video belongs to exactly one user.

\subsection{Authentication and Authorisation}

All protected endpoints require a valid JWT Bearer token in the HTTP
\texttt{Authorization} header. The \texttt{auth} middleware verifies the
token's signature using the \texttt{JWT\_SECRET} environment variable,
extracts the \texttt{userId} and \texttt{role} claims, and attaches them
to \texttt{req.user}. Token expiry is set to seven days.

The \texttt{admin} middleware extends \texttt{auth} by additionally checking
that \texttt{req.user.role === 'admin'}, returning HTTP~403 if not. Admin-only
routes include user management (\texttt{/api/admin/users}) and audit log
access.

Password hashing uses \texttt{bcryptjs} with a cost factor of 12, as
recommended by OWASP for 2025 hardware~\cite{owasp2021}. Hashing and
comparison are performed in Sequelize model hooks (\texttt{beforeCreate}
and \texttt{beforeUpdate}), ensuring that plaintext passwords never reach
the database layer.

\subsection{Video Processing}

When a video file is uploaded, the server performs three asynchronous
operations using \texttt{fluent-ffmpeg}~\cite{ffmpeg2023}:

\begin{enumerate}
  \item \textbf{Thumbnail generation:} Extracts a frame at the 10-second
  mark and saves it as a JPEG in the \texttt{uploads/thumbnails/} directory.
  \item \textbf{Metadata extraction:} Reads codec, resolution, frame rate,
  and duration from the video container.
  \item \textbf{Status update:} Updates the Video record's \texttt{status}
  field from \texttt{processing} to \texttt{ready} upon completion, or
  \texttt{error} if FFmpeg fails.
\end{enumerate}

For YouTube-imported videos, metadata is fetched from the YouTube oEmbed
API using the \texttt{ytdl-core} library, which also provides the video
thumbnail URL directly.

\section{Frontend Implementation}

\subsection{Application Structure}

The React frontend is a TypeScript SPA built with Vite~\cite{vite2023}. The
application is organised into three primary route-level components:

\begin{itemize}
  \item \textbf{Login / Register.} Authentication forms with client-side
  validation using React controlled components.
  \item \textbf{Dashboard.} Displays all videos owned by the authenticated
  user, organised into user-managed folders with a virtual trash bin
  (30-day retention). Provides global search, one-click H5P export, and a
  video visit counter.
  \item \textbf{Editor.} The core authoring interface, described in detail
  below.
\end{itemize}

State management is handled using two Zustand stores: \texttt{authStore}
(authentication state and JWT token) and \texttt{editorStore} (current video,
H5P elements, AI suggestions, upload progress, and streaming status).

\subsection{The Editor Interface}

The editor is a single-screen interface with three vertical panels,
implementing the co-location design principle derived from Chandler and
Sweller's split-attention effect research~\cite{chandler1991} and Garrett's
skeleton-plane interface organisation~\cite{garrett2010}:

\begin{enumerate}
  \item \textbf{Left panel: Video source and upload.} Provides drag-and-drop
  video upload, YouTube URL input, and a video metadata summary (title,
  duration, status).

  \item \textbf{Centre panel: Video player and H5P timeline.} Displays the
  video using the HTML5 \texttt{<video>} element (or an embedded YouTube
  iframe), with playback controls and a \emph{seek-to-timestamp} button.
  Below the player, the H5P Timeline lists all existing interactions with
  their timestamps, types, and quick-edit controls.

  \item \textbf{Right panel: AI suggestions.} Displays the list of AI-generated
  suggestions returned by the most recent analysis. Each suggestion card
  shows the timestamp, H5P type, question text, Bloom's taxonomy level,
  and the AI's reasoning. Instructors can accept (injecting the suggestion
  into the H5P timeline), reject, or edit each suggestion individually.
\end{enumerate}

The AI analysis is initiated by clicking the ``AI Analyse'' button, which
opens the transcript source selector. The frontend opens an SSE connection
to \texttt{/api/ai/analyze-stream}; streaming tokens are accumulated and
parsed into partial suggestion objects that appear progressively in the right
panel as the LLM generates them.

\subsection{Type Safety and API Client}

The frontend communicates with the backend through a typed API client
(\texttt{src/lib/api.ts}) that declares TypeScript interfaces for every
request and response object~\cite{typescript2023}. TypeScript's static type
system catches type mismatches between the frontend's expectations and the
backend's JSON schemas at compile time rather than at runtime, which is
particularly valuable in this project because the AI pipeline involves
several distinct JSON schemas (transcript segments, AI suggestions, and H5P
content parameters) that must remain consistent across the service
boundary~\cite{typescript2023}.

The \texttt{AISuggestion} type, for example, mirrors the Zod schema used
by the AI service on the backend:

\begin{lstlisting}[language=TypeScript,caption={AISuggestion TypeScript interface (6 supported types)}]
type H5PInteractionType =
  'MultiChoice' | 'TrueFalse' | 'FillBlanks'
  | 'Matching' | 'DragText' | 'MarkWords';

interface AISuggestion {
  id: string;
  timestamp: number;
  type: H5PInteractionType;
  h5pLibrary: string;
  config: Record<string, unknown>;
  reason: string;
  status: 'pending' | 'accepted' | 'rejected';
}
\end{lstlisting}

The platform supports six H5P interaction types in total, all of which
are available for both AI-assisted generation and manual authoring.
Five types (\texttt{MultiChoice}, \texttt{TrueFalse}, \texttt{FillBlanks},
\texttt{DragText}, \texttt{MarkWords}) are generated throughout the video
based on the content pattern matrix. The sixth type, \texttt{Matching},
is reserved by the AI for a dedicated \emph{Video Recap} topic that is
appended \emph{after} all content topics have ended. The system prompt
instructs the model to set this topic's \texttt{start} equal to the end
time of the final content topic and its \texttt{end} equal to the last
transcript timestamp. Its question covers 4--5 key concept--definition
pairs drawn from across the entire lecture, serving as a
whole-video knowledge-consolidation exercise~\cite{anderson2001}.

\section{Inclusive Design for Non-Technical Educators}
\label{sec:inclusive_design}

A central design requirement established during the requirements analysis
(Section~\ref{sec:requirements}) was that the platform must be operable by
instructors with limited technical experience, including older faculty members
who are accustomed to conventional slide-based or face-to-face teaching.
The WordPress H5P baseline workflow required users to navigate two separate
browser tabs, understand WordPress post concepts, and manually configure nested
sub-screens for each interaction---a sequence that produced a 30\% completion
rate among the pilot group and a mean SUS score of 38.0~\cite{brooke1996},
well below the ``poor usability'' threshold of 51. This section documents the
specific design and engineering decisions made to lower that barrier.

\subsection{Cognitive Load Reduction Through Interface Simplification}

Sweller's cognitive load theory distinguishes between \emph{intrinsic} load
(inherent to the subject matter) and \emph{extraneous} load (imposed by a
poorly designed interface)~\cite{sweller1988}. The platform's interface was
designed to minimise extraneous load through four strategies:

\begin{enumerate}
  \item \textbf{Single-screen authoring.} All authoring activities---video
  upload, transcript review, AI analysis, interaction creation, and H5P
  export---occur on a single three-panel screen. Instructors never navigate
  away from the editor, eliminating the context-switching that was identified
  as the primary pain point in the WordPress baseline~\cite{chandler1991}.

  \item \textbf{Guided type selection.} The interaction-type picker presents
  each of the six question types with a colour-coded icon and a plain-English
  description of \emph{when to use it} (e.g.\ ``Absolute facts or rules
  students confirm as true or false''). Instructors do not need to understand
  H5P library names or technical taxonomy; the design language of the picker
  maps pedagogical intent to a concrete choice~\cite{norman1988}.

  \item \textbf{Progressive disclosure.} The editor form shows only the fields
  relevant to the selected question type. A \texttt{MultiChoice} form shows a
  question field and four option inputs; a \texttt{TrueFalse} form shows a
  statement and a True/False toggle. Unrelated fields are never visible,
  reducing the number of decisions an instructor must make per
  interaction~\cite{nielsen1994}.

  \item \textbf{Inline preview.} \texttt{FillBlanks}, \texttt{DragText}, and
  \texttt{MarkWords} fields render a live preview of how the asterisk-marked
  text will appear to students, so instructors can verify their intent without
  publishing or previewing in a separate window.
\end{enumerate}

\subsection{Interaction List Transparency}

The H5P interactions panel displays each existing interaction with its type
badge, timestamp, and a preview of the question text (truncated to one line).
This allows instructors to review the full set of interactions at a glance
without opening each one individually. The numbered position indicators use
orange dots with white ring borders, deliberately echoing the seek-bar markers
on the video timeline so that instructors perceive the interaction list and the
video player as spatially related representations of the same
content~\cite{chandler1991}.

\subsection{Safe Navigation with Discard Warnings}

When an instructor begins filling in a new interaction form and then clicks the
back button, the platform checks whether any field has been modified. If the
form is dirty, an amber warning banner appears inline (rather than as a modal
dialog or browser alert) with two clearly labelled options: ``Keep editing''
and ``Discard''. This pattern follows Nielsen's error-prevention
heuristic~\cite{nielsen1994}: the system does not silently discard work, nor
does it block navigation with a system dialog that breaks focus.

\subsection{Backend Performance for Responsive Feedback}

Older instructors are more likely to abandon a workflow when response times are
perceptible~\cite{nielsen1994}. Three backend decisions directly address this:

\begin{enumerate}
  \item \textbf{SQLite with in-process access.} Because SQLite runs in the same
  process as the Express server, read queries have sub-millisecond latency with
  no network round-trip to a database server~\cite{sqlite2023}. Dashboard page
  loads and video metadata fetches are typically below 30~ms.

  \item \textbf{Groq primary provider.} Groq's LPU inference hardware delivers
  AI analysis results in 3--8~seconds for a 20-minute lecture transcript,
  compared with 15--30~seconds for an equivalent Claude request. The
  platform's provider priority chain (Groq $\to$ Ollama $\to$ Claude) ensures
  the fastest available provider is always used first.

  \item \textbf{Server-Sent Events streaming.} Rather than requiring the
  instructor to wait silently for the full AI response, the SSE streaming
  endpoint emits progress messages (``Identifying topics\ldots'',
  ``Generating questions\ldots'') and partial results as they arrive. This
  continuous feedback prevents the blank-screen waiting period that is a common
  cause of instructor abandonment in web-based authoring tools~\cite{davis1989}.
\end{enumerate}

\subsection{Accessibility and Visual Design}

The platform follows a \emph{purposeful restraint} visual language: a white
background with a single accent colour (\texttt{\#f5832a} orange), generous
padding, and 14--16~px body text. Each of the six question types is assigned a
distinct pastel colour token (blue, green, purple, teal, amber, indigo) so
that instructors can recognise interaction types at a glance without reading
the label. Dark mode is supported via Tailwind CSS's \texttt{dark:} variant
and a user-level preference persisted in \texttt{localStorage} via the Zustand
settings store, accommodating instructors who work in low-light environments or
who have photosensitivity.

It converts a raw video transcript into a validated, Bloom's-labelled list

\subsection{Stage 1: Transcript Acquisition}

Transcript acquisition is handled by the \texttt{transcriptExtraction.js}
service, which supports three source mechanisms:

\begin{enumerate}
  \item \textbf{YouTube automatic captions} (primary for YouTube-sourced
  videos). The \texttt{youtube-transcript} npm package fetches timestamped
  caption segments directly from the YouTube API using the video's 11-character
  ID. Segments are normalised into a standard format:
  \texttt{\{start: number, end: number, text: string\}}.

  \item \textbf{Uploaded caption file} (primary for uploaded video files).
  Instructors may upload a WebVTT (\texttt{.vtt}) file alongside their video.
  The service parses the VTT format and normalises segments.

  \item \textbf{Whisper audio transcription} (fallback for uploaded files
  without captions). The service invokes \texttt{faster-whisper} via a
  Python subprocess, passing the video file path and the target language.
  The resulting JSON transcript is normalised into the standard segment
  format. Whisper availability is checked at startup and reported via the
  \texttt{GET /api/ai/status} endpoint~\cite{radford2023}.
\end{enumerate}

All three sources produce the same \texttt{TranscriptSegment[]} structure,
ensuring that the downstream AI stage is source-agnostic.

\subsection{Stage 2: Segment Formatting}

The \texttt{formatSegmentsForPrompt()} function in \texttt{aiService.js}
converts the normalised segment array into a human-readable transcript
string with timestamp labels. Each line takes the format:

\begin{lstlisting}[language=JavaScript,caption={Transcript segment formatting with raw-second timestamps}]
// Input segment: { start: 330, end: 345, text: "Photosynthesis converts..." }
// Output line:
"[05:30 (330s) -> 05:45 (345s)] Photosynthesis converts..."
\end{lstlisting}

Each segment line embeds \emph{both} the human-readable \texttt{MM:SS}
form \emph{and} the raw integer seconds in parentheses. The system prompt
explicitly instructs the model to use the raw seconds integer as the
\texttt{startTime} field in its JSON output, eliminating the rounding
errors that arise when models reparse ``MM:SS'' strings~\cite{white2023}.

\subsection{Stage 3: Two-Step AI Prompt and Question-Type Assignment}
\label{sec:stage3}

The AI system prompt in \texttt{aiService.js} adopts a two-step
\emph{output automater} pattern~\cite{white2023} that separates topic
discovery from question generation, constraining the model's degrees of
freedom at each step and thereby improving output consistency.

\subsubsection{Step 1 --- Topic Segmentation}

In the first step the model receives the formatted transcript and is
instructed to produce a hierarchical topic outline rather than a flat
list of suggestions. The required output structure is a JSON array of
2--5 top-level topics, each carrying its timestamp span, a Bloom's
taxonomy level~\cite{anderson2001}, a difficulty rating (1--3), and
1--3 subtopics. Every topic node and every subtopic node is associated
with \emph{exactly one} question:

\begin{lstlisting}[language=JSON,caption={Required JSON output structure for Step 1 (topic segmentation)}]
[
  {
    "topic": "Photosynthesis Overview",
    "startTime": 330,
    "endTime": 345,
    "bloomsLevel": "Remember",
    "difficulty": 1,
    "subtopics": [
      {
        "subtopic": "Light-dependent reactions",
        "startTime": 360,
        "endTime": 380,
        "bloomsLevel": "Understand",
        "difficulty": 2,
        "question": { ... }
      }
    ],
    "question": { ... }
  }
]
\end{lstlisting}

This hierarchical structure mirrors the cognitive organisation of the
lecture rather than imposing an arbitrary spacing constraint, and has
been shown to align more closely with Bloom's taxonomy as a framework for
formative assessment design~\cite{anderson2001}.

\subsubsection{Step 2 --- Question Generation via Pattern Matrix}

In the second step the system prompt provides the model with a
\emph{pattern matrix} that deterministically maps observable
characteristics of each topic's content to one of three H5P question
types. The pattern matrix is reproduced verbatim from the
\texttt{AI\_SYSTEM\_PROMPT} constant:

\begin{lstlisting}[language={},caption={Pattern matrix from the AI system prompt (Step 2)}]
Generate EXACTLY ONE question per topic/subtopic using this pattern matrix:

  Content characteristic                     Question type
  -----------------------------------------------  ----------
  Definition / technical term                      FillBlanks
    ("X is defined as...", "Y stands for...")
  Binary fact / absolute rule                      TrueFalse
    ("always", "never", a true/false claim)
  List / comparison / process / category           MultiChoice
    (multiple items, relationships, steps)
  Sequence / ordered steps / procedure             DragText
    (steps that must go in a specific order)
  Vocabulary / key term identification             MarkWords
    (important terms embedded in a passage)
  Standalone ``Video Recap'' appended after all topics  Matching
    (4-5 concept-definition pairs drawn from the full video)

For FillBlanks: wrap the key term with asterisks (*term*)
  so it becomes a fill-in-the-blank blank.
For TrueFalse: set the "correct" field to the boolean
  truth value of the statement.
For MultiChoice: provide exactly four options,
  mark exactly one "correct": true; source the three
  distractors from nearby content in the transcript.
For DragText: wrap each draggable word/phrase in *asterisks*;
  taskDescription must describe the ordering task.
For MarkWords: wrap each key term in *asterisks*;
  include 2-5 marked terms; taskDescription tells students
  what category of term to look for.
For Matching: ONLY the last top-level topic uses this type;
  provide 4-5 pairs covering key concepts from the whole video;
  taskDescription must frame this as an end-of-video review.
\end{lstlisting}

each schema.

The pattern matrix reduces the model's output to a choice among three
structured templates, each with a precisely defined JSON schema. This
constrained generation strategy is consistent with the
\emph{output automater} prompt-engineering pattern described by
White et al.~\cite{white2023}, in which the LLM is asked to fill in a
template rather than compose freeform text, significantly reducing
hallucination of unknown field names.

\subsubsection{Provider Selection and Prompt Adaptation}

The AI generation is dispatched to three providers in priority order:

\begin{enumerate}
  \item \textbf{Groq} (primary). The Groq cloud API is contacted first
  using the \texttt{llama-3.3-70b-versatile} model via the
  \texttt{groq-sdk} client. Groq provides free-tier inference with
  sub-second token generation, making it the default provider for
  production use. The two-step system prompt is used directly.

  \item \textbf{Ollama} (local fallback). If the Groq request fails or
  the \texttt{GROQ\_API\_KEY} environment variable is absent, the
  \texttt{aiServiceOllama.js} service contacts the Ollama REST API at
  \texttt{http://localhost:11434}. Because open-weight models such as
  Mistral-7B respond less reliably to abstract instructions than to
  concrete examples, the Ollama path uses a \emph{separate few-shot
  prompt} (\texttt{buildOllamaPrompt()}) that replaces the abstract
  pattern matrix with a fully worked example showing input transcript
  segments and the expected JSON output~\cite{brown2020}. This
  in-context learning approach compensates for the reduced
  instruction-following capability of smaller open-weight models.

  \item \textbf{Anthropic Claude} (cloud fallback). If Ollama is also
  unavailable, the \texttt{@anthropic-ai/sdk} client calls
  \texttt{claude-3-5-sonnet-20241022}~\cite{anthropic2024} using the
  same two-step system prompt as Groq.
\end{enumerate}

The frontend receives an identical suggestion structure regardless of
which provider was used, preserving the provider-agnostic design
goal stated in Section~\ref{sec:architecture}.

\subsection{Stage 4: Zod Validation and Enrichment}

The raw LLM output is parsed with \texttt{JSON.parse()} and validated
against a set of Zod schemas that enforce both structural correctness
and type-specific constraints~\cite{white2023}:

\begin{lstlisting}[language=JavaScript,caption={Zod schemas for hierarchical AI output validation}]
const QuestionSchema = z.object({
  type: z.enum(['MultiChoice', 'TrueFalse', 'FillBlanks',
               'DragText', 'MarkWords', 'Matching']),
  question: z.string().min(1),
  bloomsLevel: z.enum([
    'Remember','Understand','Apply','Analyse','Evaluate','Create'
  ]),
  // Type-specific fields (validated at enrichment time):
  // MultiChoice: answers array with 4 options, 1 correct
  // TrueFalse:   correct boolean
  // FillBlanks:  text with *asterisk*-wrapped blank
  config: z.record(z.unknown()),
  reason: z.string()
});

const TopicSchema = z.lazy(() => z.object({
  topic: z.string(),
  startTime: z.number().nonnegative(),  // raw seconds integer
  endTime:   z.number().nonnegative(),
  bloomsLevel: z.string(),
  difficulty:  z.number().int().min(1).max(3),
  question:  QuestionSchema,
  subtopics: z.array(TopicSchema).optional()
}));

const ResponseSchema = z.array(TopicSchema);
\end{lstlisting}

The recursive \texttt{TopicSchema} (via \texttt{z.lazy()}) validates the
full topic/subtopic hierarchy. Any topic node that fails validation is
discarded individually rather than invalidating the entire response,
maximising the number of usable suggestions recovered from partial
outputs. Valid nodes are then \emph{enriched}: each receives a
system-generated UUID, the H5P library identifier resolved from
\texttt{H5P\_TYPE\_MAP} (e.g., \texttt{H5P.MultiChoice 1.16}), and a
status of \texttt{pending}. The enriched list is streamed to the
client via Server-Sent Events (SSE) or returned as a single JSON
response depending on the endpoint called.

\subsection{Stage 5: Suggestion Review and Injection}

The \texttt{POST /api/ai/inject} endpoint accepts an array of accepted
suggestions. The \texttt{aiInjectionService.js} service translates each
suggestion's \texttt{config} object into the format expected by
\texttt{h5pService.createTimeBasedContent()}, creates the H5P content
record, and appends a \texttt{\{contentId, timestamp, type\}} entry to the
Video's \texttt{h5pContent} JSON array. The result is returned to the
frontend, which updates the H5P timeline immediately.

\section{H5P Integration}

\subsection{Lumieducation H5P Server Library}

The \texttt{@lumieducation/h5p-server} library~\cite{lumieducation2023}
provides the following H5P capabilities as a Node.js service:

\begin{itemize}
  \item \textbf{Library management.} H5P library ZIP archives are
  automatically downloaded and cached in the \texttt{h5p-libraries/}
  directory on first use. Library versions are locked per platform version.

  \item \textbf{Content CRUD.} H5P content is stored as JSON parameter
  documents in the \texttt{h5p-content/} directory, indexed by a
  system-generated content ID.

  \item \textbf{Package export.} The library generates standards-compliant
  \texttt{.h5p} ZIP archives containing the library files, content JSON,
  and media assets. These archives are identical in structure to those
  produced by the WordPress H5P plugin and are importable into Moodle,
  Canvas, and any other LTI-compatible LMS.

  \item \textbf{Preview rendering.} The \texttt{@lumieducation/h5p-express}
  integration mounts an H5P rendering router at \texttt{/h5p/}, which
  produces the HTML/JavaScript bundle required to embed and play H5P content
  in the browser's preview panel.
\end{itemize}

\subsection{Time-Based Content Creation}

The \texttt{h5pService.createTimeBasedContent()} function is the key
integration point between the AI pipeline and the H5P layer. It wraps the
library's content creation API to associate a content ID with a timestamp
and the parent video ID. The resulting H5P content record specifies the
H5P library identifier (e.g., \texttt{H5P.MultiChoice 1.16}), the content
parameters as a JSON object, and metadata (title, license). The association
between content and timestamp is stored in the Video's \texttt{h5pContent}
JSON array rather than inside the H5P content record itself, keeping the
H5P content portable.

\subsection{Authentication Flow}

Figure~\ref{fig:seq_auth} shows the complete sequence of interactions for
the registration, email verification, login, and protected-request flows.

\begin{figure}[H]
  \centering
  \resizebox{\linewidth}{!}{\input{figures/fig_sequence_auth}}
  \caption{Sequence diagram: user registration, email verification, login,
           and authenticated API request}
  \label{fig:seq_auth}
\end{figure}

On registration, the password is bcrypt-hashed (cost factor 12) before
storage and the account is set to inactive pending email verification. A
six-digit code generated by \texttt{crypto.randomInt} is emailed to the
registered address with a ten-minute TTL. On successful verification, the
account is activated. On login, the provided password is compared with the
stored hash using \texttt{bcrypt.compare()}; on success, the server signs
a JWT~\cite{jwt2015} containing \texttt{userId}, \texttt{role}, and
\texttt{iat}/\texttt{exp} claims and returns it to the client. The client
attaches the token as a \texttt{Bearer} header on all subsequent API requests,
and the \texttt{authenticateToken} middleware verifies the signature on every
protected route.

\subsection{Password Reset}

The password reset flow generates a cryptographically random token
(\texttt{crypto.randomBytes(32).toString('hex')}), stores its bcrypt hash
in \texttt{resetToken} with a one-hour expiry in \texttt{resetTokenExpiry},
and sends the plaintext token to the user's registered email address. The
reset endpoint verifies the provided token against the stored hash and
clears both fields on success.
