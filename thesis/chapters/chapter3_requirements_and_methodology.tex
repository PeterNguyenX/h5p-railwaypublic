\chapter{Methodology}

This chapter describes how the research was designed and executed. It covers
the overall research design, the requirements analysis process, the
user-centred design methodology, the software development approach, and the
evaluation protocol.

% ─────────────────────────────────────────────────────────────────────────────
\section{Research Design}

This research adopts a \emph{design science} paradigm~\cite{sommerville2016},
in which the primary contribution is an artefact---the H5P interactive video
platform---that is created, described, and evaluated. Design science research
is appropriate for projects that aim to solve a concrete problem for a
defined stakeholder group (university instructors at VNU-HCM) by building
and evaluating a purposeful artefact (a web-based authoring system).

The research combines two methodological phases:

\begin{enumerate}
  \item \textbf{Constructive phase.} User requirements are elicited,
  the system is designed and implemented, and the AI pipeline is built and
  integrated.

  \item \textbf{Evaluative phase.} A comparative usability study measures
  the artefact's performance against the incumbent WordPress-based H5P
  workflow on four metrics: task completion rate, time-on-task, error rate,
  and SUS score.
\end{enumerate}

An \emph{agile development methodology} was adopted for the constructive
phase, using short iterative cycles of 2--3 weeks each~\cite{beck2001}. Each
cycle produced a testable increment of the platform, and informal
walkthroughs at the end of each cycle informed the next design iteration.
This approach was chosen because the interaction between the AI pipeline and
the H5P authoring workflow could not be fully specified in advance; some
requirements emerged only during implementation.

five university instructors at HCMIU to understand their current H5P

\section{User-Centred Design Process}

The interface was designed using a three-stage user-centred design process
following the principles established in Section~2.4~\cite{garrett2010,
norman1988,nielsen1994}.

\subsection{Stage 1: Conceptual Design}

In the conceptual design stage, the pain points and requirements were
translated into high-level user flow diagrams for the two primary use cases:
(1)~creating an interactive video manually, and (2)~using the AI pipeline
to generate and review suggestions. These flows were reviewed against
Nielsen's usability heuristics~\cite{nielsen1994} to identify potential
sources of extraneous cognitive load before any interface sketches were
produced.

Figure~\ref{fig:workflow} presents a side-by-side comparison of the
WordPress-based baseline workflow (ten steps, 47 interface interactions) and
the redesigned platform workflow (seven steps, approximately eight interactions).
The reduction in interaction count is the primary mechanism through which
extraneous cognitive load is reduced, consistent with Chandler and Sweller's
integrated-format principle~\cite{chandler1991}.

\begin{figure}[H]
  \centering
  \resizebox{\linewidth}{!}{\input{figures/fig_workflow_comparison}}
  \caption{Authoring workflow comparison: WordPress H5P plugin (left,
           baseline) versus the redesigned AI-ActivEdu platform (right).
           Red annotations indicate identified pain points; green annotations
           indicate design improvements.}
  \label{fig:workflow}
\end{figure}

The most significant design decision at this stage was to co-locate the video
player, the timestamp capture button, and the question editor on a single
screen. This directly addresses the split-attention effect identified in the
literature (Section~2.5) and eliminates the requirement to hold timestamp
information in working memory while navigating between screens.

\subsection{Stage 2: Wireframing and Heuristic Evaluation}

Low-fidelity wireframes were produced for the dashboard, the editor, and
the AI suggestion review panel. These wireframes were evaluated against
Nielsen's heuristics~\cite{nielsen1994} with a focus on:

\begin{itemize}
  \item \textbf{Visibility of system status:} Every asynchronous operation
  (video upload, AI analysis, package export) must display a progress
  indicator with status text.
  \item \textbf{Error prevention:} All form inputs must be validated
  client-side before submission; the submit button must be disabled until
  all required fields are valid.
  \item \textbf{User control and freedom:} Users must be able to cancel
  any in-progress AI analysis without reloading the page.
  \item \textbf{Recognition over recall:} Question types must be presented
  as labelled tiles with icons, not as a dropdown menu requiring the user
  to remember H5P type names.
\end{itemize}

\subsection{Stage 3: Prototype Testing and Iteration}

A functional prototype implementing the core editor workflow was produced
after the first development cycle and tested informally with two IT students.
The session used a think-aloud protocol in which participants verbally
described their intentions as they attempted to create a simple interactive
video. Three usability problems were identified and resolved before the
formal evaluation:

\begin{enumerate}
  \item The timestamp input field was not automatically populated with the
  current playback position. Fix: added an auto-populate button that captures
  the current time.
  \item The AI analysis status messages were not visible without scrolling
  down. Fix: anchored the status panel to the top of the suggestions column.
  \item The ``Export H5P'' button label was unclear. Fix: relabelled to
  ``Download .h5p package'' with a tooltip explaining LMS compatibility.
\end{enumerate}

\section{Development Methodology}

\subsection{Technology Selection}

Technology selection was guided by four criteria: community maturity,
alignment with the H5P server library's Node.js requirement, developer
familiarity, and suitability for the AI pipeline.

\begin{itemize}
  \item \textbf{Frontend: React~18 + TypeScript + Vite.}
  React was selected because it is the most widely adopted JavaScript UI
  framework, providing a large ecosystem of compatible libraries and
  extensive documentation~\cite{react2023}. TypeScript was mandatory because
  the AI pipeline involves multiple JSON schemas (transcript segments,
  AI suggestions, H5P content parameters) that must be kept consistent
  across client and server~\cite{typescript2023}. Vite was chosen as the
  build tool for its sub-second hot module replacement~\cite{vite2023}.

  \item \textbf{Backend: Node.js + Express.js.}
  Node.js was selected to maintain a single language across the stack and to
  satisfy the \texttt{@lumieducation/h5p-server} dependency~\cite{nodejs2023,
  expressjs2023}. Express.js provides a minimal, middleware-based HTTP
  framework that integrates cleanly with the H5P server library.

  \item \textbf{Database: SQLite via Sequelize ORM.}
  SQLite was selected for its zero-configuration deployment and its
  sufficiency for the expected data volumes (hundreds of users, thousands
  of videos)~\cite{sqlite2023}. The Sequelize ORM provides a type-safe
  model layer, migration support, and future flexibility to switch to
  PostgreSQL if institutional scale demands it~\cite{sequelize2023}.

  \item \textbf{AI: Anthropic Claude + Ollama.}
  Anthropic Claude was selected as the cloud AI provider because of its
  strong instruction-following and reliable JSON output~\cite{anthropic2024}.
  Ollama was added as a first-choice local provider to enable cost-free,
  privacy-preserving operation in environments where API access is
  unavailable~\cite{brown2020}.
\end{itemize}

\section{Evaluation Methodology}

\subsection{Study Design}

The evaluation employed a within-subject comparative usability study with
ten participants, following the protocol recommended by Nielsen for small
usability studies~\cite{nielsen1994}. Each participant completed an
identical set of tasks on both the new platform and the WordPress H5P
plugin, in counterbalanced order, with a 30-minute rest between sessions to
reduce learning effects.

\subsection{Participants}

Participants were ten students enrolled in Information Technology programmes
at HCMIU, recruited voluntarily. Serving as educator proxies is a standard
and accepted approach in early-stage usability evaluation for educational
technology~\cite{nielsen1994}: IT students are familiar with the concept of
content authoring tools and can be briefed on the instructor role without
extensive domain training. Table~\ref{tab:participants} summarises
participant characteristics.

\subsection{Task Scenarios}

Participants were given a standardised task description:

\begin{quote}
  \itshape You are a lecturer preparing a short interactive video on a
  scientific topic. You have been given a 5-minute lecture video. Your task
  is to: (1)~upload or link the video, (2)~add at least three H5P questions
  at appropriate timestamps, and (3)~export the H5P package for use in the
  university's LMS. Complete these tasks as you would if preparing actual
  teaching materials.
\end{quote}

For the new platform, participants were additionally instructed to:
(4)~use the AI analysis feature and review the generated suggestions before
adding their own questions.

\subsection{Metrics}

Four primary metrics were collected:

\begin{enumerate}
  \item \textbf{Task completion rate (TCR):} The percentage of participants
  who completed all three sub-tasks without abandonment. A task was scored
  as incomplete if the participant explicitly gave up or if the session
  reached the 20-minute time limit without completion.

  \item \textbf{Time-on-task (ToT):} The elapsed time from task
  commencement to the point at which the participant exported a valid
  \texttt{.h5p} package, measured in minutes and seconds.

  \item \textbf{Error count:} The number of observable errors (incorrect
  actions requiring correction, error messages triggered, or navigational
  dead-ends) recorded by the observer.

  \item \textbf{SUS score:} Administered immediately after each session.
  A SUS score above 68 is considered above average; above 80 is
  excellent~\cite{brooke1996}.
\end{enumerate}

Qualitative data were collected through think-aloud verbalisations during
the sessions and a brief semi-structured interview administered after both
sessions were complete.

\subsection{Baseline System}

The baseline was the WordPress H5P plugin (version 1.15.8) installed on a
standard LAMP stack, configured to match the environment used by VNU-HCM
faculty. Participants were given a brief 5-minute orientation to the
WordPress interface before starting the task, equivalent to the orientation
they would receive from a standard university ICT induction.
