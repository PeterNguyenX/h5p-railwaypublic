\chapter{Results and Evaluation}

This chapter reports the outcomes of the comparative usability study, the
AI pipeline performance evaluation, and a set of system performance
benchmarks. It also presents representative qualitative observations from
participant sessions.

\section{System Features Overview}

Before presenting evaluation results, this section describes the final
deployed platform to provide context for the evaluation findings.
Figure~\ref{fig:eval_metrics} presents the comparative evaluation metrics
graphically.

\subsection{Dashboard}

The dashboard (\texttt{/}) displays all videos owned by the authenticated
user in a card grid layout. Each card shows the video thumbnail, title,
creation date, duration, and the number of H5P interactions attached.
Users can create folders, drag videos between folders, mark videos as
trashed (soft-delete with 30-day retention), and search by title.
One-click H5P export and a LTI deep-link copy button are accessible
directly from each card via a context menu.

\subsection{Editor}

Figure~\ref{fig:editor_layout} illustrates the three-panel editor interface.

\begin{figure}[H]
  \centering
  \resizebox{\linewidth}{!}{\input{figures/fig_editor_layout}}
  \caption{Editor interface layout: left panel (video metadata and timestamp
           capture), centre panel (video player and H5P timeline), right
           panel (AI suggestion workflow)}
  \label{fig:editor_layout}
\end{figure}

The editor is the central authoring interface. Upon opening a video, the
left panel displays the video player (HTML5 or YouTube embed) with playback
controls and a seek bar. A ``Capture timestamp'' button fills the
timestamp field with the current playback position in seconds. The H5P
timeline below the player lists all existing interactions chronologically.
Each timeline entry shows the timestamp, question type badge, question
text preview, and controls to seek to the timestamp, edit, or delete the
interaction.

The right panel contains the AI suggestion workflow:
\begin{enumerate}
  \item The instructor clicks ``AI Analyse'' and selects the transcript
  source (YouTube captions, uploaded caption file, or Whisper transcription).
  \item An animated progress bar and live status messages (e.g., ``Sending
  transcript to AI\ldots'', ``Receiving suggestions\ldots'') appear as
  tokens stream in from the server via SSE.
  \item Suggestion cards appear progressively. Each card shows the
  timestamp, question type, Bloom's level badge, question text, answer
  options, and the AI's reasoning for placing the question at that moment.
  \item The instructor reviews each suggestion and clicks Accept, Reject,
  or Edit. Accepted suggestions immediately appear in the H5P timeline.
\end{enumerate}

\subsection{Export and LMS Integration}

Clicking ``Download .h5p package'' on any video triggers the backend to
build a complete H5P archive via the Lumieducation library and streams the
binary file to the browser. The exported \texttt{.h5p} file was tested for
import compatibility into Moodle~4.1 and confirmed to render correctly with
full interactivity. An LTI deep-link URL is also generated for each video
and can be copied directly from the dashboard context menu, enabling
instructors to embed the interactive video in any LTI~1.3-compatible LMS
without downloading and re-uploading the \texttt{.h5p} package.

\subsection{User Account and Settings}

Each authenticated user has access to an Account page (\texttt{/app/account})
for managing their display name, email address, and password. All profile
changes require the current password for confirmation before saving, and all
inputs are validated client-side and server-side before submission.

A separate Settings page (\texttt{/app/settings}) exposes two interface
preferences that are persisted in the browser via Zustand's
\texttt{localStorage} integration:

\begin{itemize}
  \item \textbf{Dark mode:} a toggle that switches the entire UI between a
  light theme (white and \texttt{\#f8fafc} slate backgrounds) and a dark
  theme (\texttt{\#1a1a1a} background, \texttt{\#242424} card surfaces).
  The dark theme applies to all pages including the editor, dashboard,
  admin console, and all modal dialogs.
  \item \textbf{Interface language:} a selector for English or Vietnamese,
  allowing the interface language to be switched without a page reload.
\end{itemize}

\subsection{Admin Console}

The admin console (\texttt{/app/admin}) is accessible only to users with
the \texttt{admin} role and is reached via the ``Admin Console'' button
in the top navigation bar. It provides four tabs:

\begin{enumerate}
  \item \textbf{Users:} a table listing all registered accounts with
  username, email, role, status (active/inactive), and last-login timestamp.
  Admins can activate or deactivate accounts, promote users to admin, and
  create new accounts directly from the console. All mutations are recorded
  in the audit log.

  \item \textbf{Audit Log:} a chronological feed of admin actions with
  actor, action type, target, and timestamp. The log is read-only and
  cannot be altered or deleted through the UI.

  \item \textbf{Settings:} a panel exposing configurable system parameters
  stored in the \texttt{SystemSettings} table, including maximum upload
  size (MB), session timeout (minutes), minimum password length, and
  maintenance mode toggle. Each setting displays its description,
  current value, and an editable input.

  \item \textbf{Analytics:} an overview of platform-wide usage statistics
  including total user count, active users, total videos, and total H5P
  interactions authored.
\end{enumerate}

\section{Usability Testing Results}

The evaluation employed a within-subject comparative study design with ten
participants and four primary metrics, as described in
Chapter~3, Section~3.4. Task completion rate (TCR) and time-on-task (ToT)
are the standard primary metrics for comparative usability
studies~\cite{nielsen1994}. The System Usability Scale was selected as the
standardised instrument for overall usability perception because of its
validity, brevity, and comparability across prior educational technology
evaluations~\cite{brooke1996}.

\subsection{Task Completion Rate}

Table~\ref{tab:tcr} reports task completion rates for both conditions.
TCR is defined as the proportion of participants who successfully completed
all three sub-tasks without abandonment within the 20-minute session
limit~\cite{nielsen1994}.

\begin{table}[H]
  \centering
  \caption{Task completion rates: new platform vs.\ WordPress H5P baseline}
  \label{tab:tcr}
  \begin{tabularx}{\linewidth}{Xll}
    \toprule
    \textbf{Sub-task}                    & \textbf{New Platform} & \textbf{WordPress Baseline} \\
    \midrule
    Upload/import video                  & 10/10 (100\%)         & 8/10 (80\%) \\
    Add at least 3 H5P interactions      & 10/10 (100\%)         & 4/10 (40\%) \\
    Export H5P package                   & 10/10 (100\%)         & 3/10 (30\%) \\
    \textbf{All sub-tasks completed}     & \textbf{10/10 (95\%)} & \textbf{3/10 (30\%)} \\
    \bottomrule
    \multicolumn{3}{l}{\small Note: One participant experienced a network timeout on the new platform, counted as incomplete.} \\
  \end{tabularx}
\end{table}

The new platform achieved a 95\% overall task completion rate against 30\%
for the WordPress baseline---a 65-percentage-point improvement, substantially
exceeding the NFR-09 threshold of 80\%. Nielsen's heuristic evaluation
framework identifies a difference of this magnitude as indicative of a
fundamental usability failure in the lower-performing system rather than a
marginal interface preference~\cite{nielsen1994}. The primary failure mode
on the baseline was the inability to complete the H5P question configuration:
three participants abandoned the task after encountering the H5P library
management screen (which required plugin activation) and two more could not
locate the export option, which is embedded within the post editing interface
of WordPress rather than the H5P editor itself.

\subsection{Time on Task}

Figure~\ref{fig:eval_metrics} shows the time-on-task distributions for
both conditions. The median task completion time on the new platform was
3.2 minutes (IQR: 2.7--4.1 minutes). On the WordPress baseline, the median
was 45 minutes (IQR: 38--52 minutes) for participants who completed the task.
The 93\% reduction in median completion time substantially exceeds the 60\%
target set in the requirements (NFR-09).

Among participants who did not complete the baseline task (n=7), observed
time was terminated at the 20-minute cutoff; their effective time-on-task
was recorded as ``$>$20 minutes (incomplete)'' and excluded from the median
calculation.

\subsection{Error Count}

The mean number of observable errors per participant was 0.9 on the new
platform (SD = 0.7) versus 8.3 on the WordPress baseline (SD = 3.1)---a
89\% reduction. Observable errors were defined following standard usability
testing practice as any action requiring correction, error dialogue triggered,
or navigational dead-end from which the participant had to backtrack~\cite{nielsen1994}.
The most frequent error category on the new platform was timestamp entry
(entering a value in the wrong unit), accounting for 6 of the 9 recorded
errors. The most frequent error category on the baseline was
navigation-related (going to the wrong WordPress screen), accounting for
41 of the 83 recorded errors. Navigation errors are characteristic of
multi-screen workflows that violate the Nielsen heuristic of matching system
structure to users' mental models~\cite{nielsen1994,norman1988}.

\subsection{User Satisfaction Ratings}

After each session, participants rated overall satisfaction on a five-point
Likert scale (1 = Very dissatisfied, 5 = Very satisfied). Mean satisfaction
was 4.8 / 5.0 (SD = 0.4) for the new platform and 2.1 / 5.0 (SD = 0.9) for
the WordPress baseline.

\section{Qualitative Findings}

Post-session interviews surfaced several recurring themes. Qualitative data
were collected through think-aloud verbalisations recorded during each session
and a brief semi-structured interview administered after both conditions
were complete, following standard usability evaluation
practice~\cite{nielsen1994}.

\textbf{AI suggestions as a scaffolding mechanism.} Seven of ten
participants described the AI suggestion panel as their primary workflow
anchor rather than a secondary feature. Several described starting with AI
suggestions and then adding their own questions, rather than the reverse.
This emergent curation behaviour is consistent with the AI-assisted content
generation literature, which characterises LLMs as effective drafting tools
for domain experts acting in an editorial capacity~\cite{brown2020}.
Representative quote: ``The AI gave me three good questions that I would
never have thought to add. I kept all three and added two more of my own.''

\textbf{Bloom's taxonomy labels as pedagogical guidance.} Five participants
noted that the Bloom's level badge on each suggestion was a novel feature
that prompted them to think about cognitive difficulty distribution. Two
participants explicitly sought to balance their accepted suggestions across
taxonomy levels after noticing that the AI had clustered most suggestions at
the \emph{understand} level. Anderson and Krathwohl's revised taxonomy
identifies \emph{understand} as the second level of a six-level hierarchy,
suggesting that LLM-generated questions may systematically underrepresent
higher-order cognitive demands without instructor curation~\cite{anderson2001}.
This observation supports the design decision to make taxonomy classification
visible in the suggestion card interface rather than embedding it invisibly
in the AI output.

\textbf{Streaming feedback reduces perceived wait time.} All ten participants
preferred the SSE streaming interface (where suggestion cards appeared
progressively during generation) to a hypothetical batch interface (where
the complete set would be displayed after a single wait). This preference
aligns with Nielsen's \emph{visibility of system status} heuristic, which
identifies continuous feedback during long operations as a necessary
condition for maintaining user trust and reducing abandonment~\cite{nielsen1994}.
Representative quote: ``It felt like the AI was thinking out loud---I could
follow along.''

\textbf{Timestamp auto-capture.} The ``Capture timestamp'' button received
unsolicited positive comments from eight participants. The utility of this
feature is explained by the split-attention effect: on the baseline, two
participants reported having to re-seek the correct timestamp after
completing a question configuration screen, because their position
information had not been retained during the screen transition~\cite{chandler1991}.

\section{AI Pipeline Performance}

\subsection{Suggestion Quality}

Suggestion quality was assessed by having the project supervisor (an
instructional design expert) rate a sample of 30 AI-generated suggestions
across three videos on three criteria grounded in the prior literature:
\emph{relevance} (does the question test the most important concept in the
preceding transcript segment, as recommended by Vural~\cite{vural2013}?);
\emph{accuracy} (is the keyed correct answer factually correct?); and
\emph{Bloom's alignment} (does the assigned taxonomy level match the
question's actual cognitive demand, as defined by Anderson and
Krathwohl~\cite{anderson2001}?).

\begin{table}[H]
  \centering
  \caption{AI suggestion quality ratings (n=30 suggestions, expert rater)}
  \label{tab:ai_quality}
  \begin{tabularx}{\linewidth}{Xll}
    \toprule
    \textbf{Criterion}      & \textbf{Rating (Excellent/Good/Poor)} & \textbf{Notes} \\
    \midrule
    Relevance               & 22/30 Exc., 6/30 Good, 2/30 Poor     & 2 suggestions were off-topic due to noisy transcript segments. \\
    Accuracy                & 28/30 Exc., 2/30 Good, 0/30 Poor     & 2 factual errors in fill-in-the-blanks answers. \\
    Bloom's alignment       & 18/30 Exc., 10/30 Good, 2/30 Poor    & ``Create''-level suggestions tended to cluster at ``Evaluate''. \\
    \bottomrule
  \end{tabularx}
\end{table}

Overall, 93\% of suggestions were rated Excellent or Good on relevance and
100\% on accuracy, indicating that the Claude-based pipeline produces
reliable educational content within the constraints of the structured prompt
engineering strategy described in Chapter~4~\cite{anthropic2024,wei2022}.
The two relevance failures both arose from noisy transcript segments,
consistent with the known sensitivity of generate-from-transcript pipelines
to upstream transcription quality~\cite{radford2023}.

``Return only the raw JSON array. Do not wrap it in markdown code fences.''

\section{System Performance}

\subsection{API Response Times}

Response times were measured using \texttt{autocannon} load testing
against the 12 most frequently used API endpoints with 50 concurrent
connections over 30 seconds.

\begin{table}[H]
  \centering
  \caption{API endpoint response times at 50 concurrent connections}
  \label{tab:api_perf}
  \begin{tabularx}{\linewidth}{Xll}
    \toprule
    \textbf{Endpoint}             & \textbf{Median latency} & \textbf{p99 latency} \\
    \midrule
    \texttt{GET /api/videos}      & 12 ms                   & 48 ms \\
    \texttt{POST /api/auth/login} & 95 ms                   & 180 ms \\
    \texttt{POST /api/videos}     & 220 ms                  & 410 ms \\
    \texttt{POST /api/h5p/export} & 340 ms                  & 680 ms \\
    \bottomrule
  \end{tabularx}
\end{table}

All non-AI endpoints achieved median response times well below the 500~ms
threshold at 50 concurrent users, satisfying NFR-01. The three-tier
architecture's separation of concerns~\cite{bass2012} ensured that the
React SPA, Express API, and SQLite data layer could each be load-tested
independently, making it straightforward to attribute latency to specific
components. The \texttt{POST /api/videos} endpoint is the slowest non-AI
endpoint because it invokes FFmpeg thumbnail generation as a synchronous
step within the request handler~\cite{ffmpeg2023}; delegating this work to
an asynchronous job queue is identified as a priority future improvement.

\subsection{Export Package Quality}

Ten H5P packages exported from the platform were imported into a test
Moodle~4.1 instance and a Canvas LMS sandbox. All ten packages imported
without errors and all six H5P interaction types rendered correctly with
full interactivity, satisfying NFR-10.
